# 部署窗口与发布协调

> 任务书："请约定部署窗口或等效机制，避免某模块正在部署时其他模块的集成测试误报失败。" "组内各模块的发布顺序须协调。"

## 为什么一次部署覆盖全部模块

本组五个镜像由同一条流水线、同一个 `IMAGE_TAG` 一起构建与部署（`deploy.sh <tag>`），不存在"M1 正在部署、M2 在跑集成测试"的交错：集成测试在构建阶段、部署之前就完成了；e2e 在部署完成并通过 `smoke.sh` 之后才触发。

## 机制

| 层 | 机制 | 作用 |
|---|---|---|
| 流水线 | 同一流水线串行执行（控制台并发控制） | 两次合并不会同时部署测试环境 |
| 主机 | `deploy.sh` 顺序执行：拉镜像 → 迁移（4 个一次性容器，`service_completed_successfully`）→ 启服务 → `smoke.sh` 全部健康才记录成功 | 迁移未完成时新代码不会接流量 |
| 测试环境 | 自动部署，无窗口限制；e2e 只在 `smoke.sh` 通过后执行 | 避免半部署状态下的误报 |
| 生产环境 | 仅在**每周三 20:00–22:00** 或评审节点前一天的约定时段，经人工审核后发布；发布前在群里通知并更新 `release.md` | 组内知情，演示前不动生产 |
| 冻结 | 每次 Review 与期末展示前 48 小时冻结生产 | 保证演示稳定 |

## 发布顺序

因为是整体部署，顺序问题转化为**契约兼容性**：

1. 契约变更（`packages/contracts`）与消费方的适配必须在同一个 `IMAGE_TAG` 里，或先发兼容版本（新增字段）再发删除。
2. schema 变更遵循 expand/contract：先加列 / 表并兼容旧代码，下一发布再删除。这样 `rollback.sh` 回到上一镜像时仍能跑在新 schema 上。
3. 跨模块写回接口（X-1、X-2）的提供方（M1）先于调用方（M2、M3）合并。
