# ADR-0011: M3 报修通过内部只读接口校验主数据

Status: implemented
Date: 2026-11-12
Related: TASK-031、REQ-M3-01、REQ-M3-02、REQ-D2-02、[ADR-0003](2026-10-25-service-topology.md)

## 问题

M3 创建工单必须确认房间与座位归属，派单必须确认被指派者是仍在岗的维修人员。M1 与 platform 分别拥有这些主数据，M3 不能跨 schema 查询。原有面向用户的 M1 列表接口依赖用户 JWT，不能作为服务间身份。

## 决定

M1 提供仅接收内部令牌的房间查询，返回有效房间 id 和有效座位 id；platform 提供仅接收内部令牌的维修人员资格查询，未知或停用用户返回 `eligible=false`。M3 通过 HTTP 调用两者，校验通过后才在自己的 schema 写工单及事件。调用超时或返回异常时拒绝写入，不猜测主数据有效性。请求和响应 DTO 放在 `packages/contracts`。

报修照片只保存可选的附件引用，不把二进制写入工单表；上传服务留给后续实现。

## 备选方案

- 转发用户 JWT 调用 M1 现有列表：省去一个接口，但把服务校验绑定到用户可见性与列表形态，也违反内部令牌调用约定。
- M3 直接读取 M1/platform schema：实现短，但破坏模块边界，迁移与权限变更会互相牵连。

## 后果

上报和派单会依赖两个上游服务的可用性；上游失败时返回网关错误，避免落入无法追溯的无效工单。跨模块契约与 M3 schema 变更需要两名人工评审。

## 验证

M1 和 platform 的内部接口各有数据库集成测试，验证内部令牌、有效记录及无效记录；M3 的数据库集成测试验证上游返回、权限、状态冲突和事件写入，迁移从空 schema 重放。
